# Plan: mev-scout Web UI + API (same repo)

## Context

- Goal: a web UI covering **all CLI capabilities** (user decision), plus an API layer (user confirmed API is needed).
- Decisions made with user:
  - UI lives in **this repo** (workspace member, shared types with core).
  - Frontend stack: **React + Vite + TypeScript** (static build served by the API).
  - API scope: **Read + operational** (start/stop CLI commands from UI).
  - Access control: **Local-only** (bind `127.0.0.1`, no auth for MVP).
  - Operational model: **Hybrid — subprocess CLI**: read endpoints query SQLite/JSON directly; operational endpoints spawn/kill the `mev-scout` binary as background jobs, capture stdout/stderr into logs.
- Architecture reference: `docs/ARCHITECTURE.md`; explorer data model: `docs/EXPLORER_UNIFIED_PLAN.md` §9–§10.

## Structure

New workspace member `api/` (crate `mev-scout-api`, binary `mev-scout-api`) + `web/` (Vite app, not a crate):

```
api/
  Cargo.toml            # axum, tokio, rusqlite (r2d2 pool), serde, serde_json, tracing
  src/
    main.rs             # bind 127.0.0.1:7600 (configurable), static file serving from web/dist
    state.rs            # AppState { db paths from Config, job registry }
    jobs.rs             # subprocess job manager: spawn, stream output, kill, list, status
    routes/
      mod.rs
      read.rs           # read-only data endpoints (SQLite + results/*.json)
      ops.rs            # operational endpoints (run jobs)
      jobs.rs           # job control endpoints
web/
  package.json  vite.config.ts  tsconfig.json
  src/
    api.ts              # typed fetch client
    App.tsx, pages/ (Dashboard, ExplorerFeed, Ops, ScannerResults, Jobs)
```

Workspace: add `"api"` to `[workspace] members` in root `Cargo.toml`.

## Data sources (read side)

- Explorer store: `core/src/explorer/store.rs` tables (`mev_ops`, `swaps`, `blocks`, `opportunities`, `rejected_candidates`, `sync_state`, `labels`, `prices`) — open read-only (WAL allows concurrent readers).
- Scanner results: `results/*.json` (`ResultsFile`), export dir from config.
- Scanner cache: `cache.db` — run manifests, discovered pools (read-only).
- API returns serde types matching `MevOpRow`, `StatsRow`, `FeedRow` (already `Serialize`).

## Endpoints

Read:
- `GET /api/health` — versions, chain, db paths exist
- `GET /api/explorer/feed?kinds=&min_profit_usd=&limit=` — tail of `mev_ops` (FeedRow)
- `GET /api/explorer/stats?since=1d|7d|30d|all` — per-kind counts/profit, daily breakdown
- `GET /api/explorer/top?by=sender|token|pool&metric=&since=&limit=` — leaderboards
- `GET /api/explorer/op/:tx_hash` — one op full detail (route_json decoded)
- `GET /api/explorer/ops?from=&to=&kind=&limit=&offset=` — paginated list
- `GET /api/explorer/validate?since=...` — reuses `explorer::validate` outputs (JSON already produced by CLI; serve parsed JSON)
- `GET /api/results` — list `results/*.json` (run_id, ts, counts)
- `GET /api/results/:run_id` — opportunities from a ResultsFile
- `GET /api/sync` — `sync_state` + `blocks_classified` head/indexed_to
- `GET /api/pools?limit=&q=` — discovered pools from cache.db

Operational (jobs over subprocess):
- `POST /api/jobs` `{ command: "run"|"live"|"fetch"|"discover"|"explorer index"|..., args: {...}, config_path? }` → job id
  - Job = `tokio::process::Command` running the `mev-scout` binary with the resolved args; stdout/stderr piped to `api/logs/{job_id}.log`.
- `GET /api/jobs` — list with status (running/finished/failed, exit code)
- `GET /api/jobs/:id` — status + last N log lines
- `GET /api/jobs/:id/log` — full log (tail-able)
- `POST /api/jobs/:id/stop` — kill process group
- Safety: one running job at a time by default (mutex), config path validated, no shell (argv array only), local bind only.

## Frontend (React + Vite + TS)

- Pages:
  1. **Dashboard** — health, sync state, latest run/live results summary.
  2. **Explorer** — live feed table (polling via `setInterval` on `/feed`, SSE optional later), stats cards (1d/7d/30d), leaderboards, op detail drawer.
  3. **Scanner Results** — runs list, opportunities table, block summary.
  4. **Jobs** — command launcher (dropdown = CLI commands with their arg forms, mirroring `cli/src/cli.rs`), job list, live log viewer.
  5. **Validate** — recall/validation report view (served JSON).
- UI libs: TanStack Table (tables), Recharts (charts), plain CSS or Tailwind (decide at impl, default Tailwind).
- Dev proxy: Vite `server.proxy` → `127.0.0.1:7600`; production: axum serves `web/dist` statically.

## Implementation steps

1. Security fix prerequisite (user should do / confirm): rotate leaked API keys in committed `mev-scout*.toml`; gitignore live config files; use `${ENV_VAR}` pattern from `mev-scout.example.toml`.
2. Remove stray `undefined/` dir; (optional) move `mev_strategies.md` → `docs/`.
3. Create `api` crate: workspace member, axum server skeleton, state with db paths from `Config` (reuse `core::config`), health endpoint.
4. Read endpoints (explorer feed/stats/top/ops/sync → `ExplorerStore`; results endpoints → parse `ResultsFile` JSON).
5. Jobs subsystem: spawn/stop/log for CLI subcommands (argv built from typed request, no shell), single-job mutex, log files under `api/logs/`.
6. Frontend scaffold (`web/`): Vite + React + TS, api client, dev proxy.
7. Pages in order: Dashboard → Explorer (feed+stats+top) → Jobs (launcher+log) → Scanner Results → Validate.
8. Static serving of `web/dist` in axum (feature-gated or always, 404 fallback to index.html).
9. Add `scripts/dev.ps1` (runs api + vite concurrently) and README section.

## Validation

- `cargo build` full workspace; `cargo clippy` clean (scripts/clippy.ps1 exists).
- `api` unit tests: read endpoints against in-memory `ExplorerStore` (reuse `open_in_memory()`), jobs endpoints with a stub command (e.g. `--version`).
- Manual: start API with real config → Dashboard shows sync state; start `explorer index` job → log streams; kill job works; feed/stats reflect indexed ops.
- Frontend: `npm run build` passes; pages render against running API.

## Risks / notes

- SQLite concurrent access: API opens read-only connections (WAL) while CLI writes — safe; avoid API writes to avoid lock contention.
- `ResultsFile` JSON parsing in API duplicates serde structs — acceptable (small), or later extract shared types crate.
- Windows: spawn must use taskkill of process tree or Job Objects for reliable stop of children (revm CLI runs are single process — `Child::kill` usually enough).
- Live config files currently contain real API keys (tracked in git) — rotate before any public exposure.

## Out of scope (explicit)

- Auth/multi-user, HTTPS, remote deployment hardening.
- SSE/WebSocket streaming for feed (MVP uses polling).
- Embedded in-process execution of core library functions (subprocess chosen).
