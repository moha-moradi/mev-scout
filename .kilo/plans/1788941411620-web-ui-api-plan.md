# Plan: mev-scout Web UI + API (same repo)

## Context

- Goal: a web UI covering **all CLI capabilities** (user decision), plus an API layer (user confirmed API is needed).
- Decisions made with user:
  - UI lives in **this repo** (workspace member, shared types with core).
  - Frontend stack: **React + Vite + TypeScript** (static build served by the API).
  - API scope: **Read + operational** (start/stop CLI commands from UI).
  - Access control: **Local-only** (bind `127.0.0.1`, no auth for MVP).
  - CSS: **Tailwind**.
  - Jobs concurrency: **single job at a time** (simple mutex).
  - Operational model: **Hybrid — subprocess CLI**: read endpoints query SQLite/JSON directly; operational endpoints spawn/kill the `mev-scout` binary as background jobs, capture stdout/stderr into logs.
- Architecture reference: `docs/ARCHITECTURE.md`; explorer data model: `docs/EXPLORER_UNIFIED_PLAN.md` §9–§10.

## Data sources (read side)

- **Explorer store**: `core/src/explorer/store.rs` tables (`mev_ops`, `swaps`, `blocks`, `opportunities`, `rejected_candidates`, `sync_state`, `labels`, `prices`) — open read-only (WAL allows concurrent readers).
- **Scanner results**: `results/*.json` (`ResultsFile`), export dir from config (`Config::output.export_path`).
- **Scanner cache**: `cache/{chain}-mev-scout.sqlite` — run manifests (`RunManifest`), discovered pools.
- API returns serde types matching `MevOpRow`, `StatsRow`, `FeedRow`, `OverviewRow`, `OpportunityRow`, `RejectedRow` (already `Serialize`).

### Operational (jobs over subprocess)

| Method | Path | Body / Params | Response | Notes |
|--------|------|---------------|----------|-------|
| `POST` | `/api/jobs` | `{ command, args }` | `{ job_id }` | 409 if job already running |
| `GET` | `/api/jobs` | — | `Vec<JobInfo>` | list all (running + finished) |
| `GET` | `/api/jobs/:id` | — | `JobInfo` | status, exit_code, run_id, created_at |
| `GET` | `/api/jobs/:id/log?tail=` | query param `tail` (default 100) | `Vec<String>` | log lines |
| `POST` | `/api/jobs/:id/stop` | — | `JobInfo` | kill process tree |

**Job = `tokio::process::Command`** running the `mev-scout` binary with resolved argv. stdout/stderr piped to `api/logs/{job_id}.log`. One running job at a time enforced by `Arc<Mutex<JobManager>>`.

**Safety**:
- No shell invocation (argv array only, `Command::new(path).args(vec![...])`)
- Config path validated (must exist, must be readable)
- Local bind only (`127.0.0.1`)
- Process tree kill on Windows: `taskkill /T /F /PID {child_pid}` (see Risks)

**Windows process tree kill**:
```rust
#[cfg(target_os = "windows")]
async fn kill_process_tree(pid: u32) -> anyhow::Result<()> {
    tokio::process::Command::new("taskkill")
        .args(["/T", "/F", "/PID", &pid.to_string()])
        .output()
        .await?;
    Ok(())
}

#[cfg(not(target_os = "windows"))]
async fn kill_process_tree(pid: u32) -> anyhow::Result<()> {
    // SIGTERM first, then SIGKILL after timeout
    nix::sys::signal::kill(unistd::Pid::from_raw(pid as i32), nix::sys::signal::Signal::SIGTERM)?;
    Ok(())
}
```

**Job → Run link**: After a job finishes with exit code 0, `JobInfo` includes `run_id: Option<String>` parsed from stdout (the CLI prints `Run ID: run_{epoch}`). The frontend can then fetch `/api/results/{run_id}`.

## Risks / notes

- **SQLite concurrent access**: API opens read-only connections (WAL) while CLI writes — safe; avoid API writes to avoid lock contention.
- **`ResultsFile` JSON parsing**: API reads `results/*.json` directly (same serde types as `MevOpportunity`). No duplication issue since the same types from `core` are used.
- **Windows process tree kill**: `Child::kill()` only kills the direct child, not grandchildren (e.g., if `mev-scout` spawns revm or async workers). Must use `taskkill /T /F /PID` on Windows. On Unix, `SIGTERM` to process group is sufficient.
- **Pool name enrichment**: CLI uses `pool_manager.get()` to resolve addresses to human-readable names (DEX + tokens). API returns raw addresses; frontend can resolve from `pools` endpoint or a future `/api/pools/address/:addr` lookup.
- **Live config files**: currently contain real API keys (tracked in git) — rotate before any public exposure. Use `${ENV_VAR}` pattern from `mev-scout.example.toml`.
- **Pagination**: MVP slices `Vec<T>` in API layer (calls full store query, then takes `offset..offset+limit`). Sufficient for local-only use with reasonable data volumes. If data grows, add paginated SQL queries to store later.
- **Validation endpoint**: `GET /api/explorer/validate` removed from MVP — `ValidationReport` requires `compute_validation()` which is expensive and re-runs the comparison. Better served by caching the JSON output from CLI `explorer validate --json` and serving the cached file, or adding a job endpoint that runs it on demand.

## Out of scope (explicit)

- Auth/multi-user, HTTPS, remote deployment hardening.
- SSE/WebSocket streaming for feed (MVP uses polling).
- Embedded in-process execution of core library functions (subprocess chosen).
- Embedded in-process explorer validation (CLI subprocess or cached JSON).
