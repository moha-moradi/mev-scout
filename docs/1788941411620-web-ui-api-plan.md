# Plan: mev-scout Web UI + API (same repo)

## Context

- Goal: a web UI covering **all CLI capabilities** (user decision), plus an API layer (user confirmed API is needed).
- Decisions made with user:
  - UI lives in **this repo** (workspace member, shared types with core).
  - Frontend stack: **React + Vite + TypeScript** (static build served by the API).
  - API scope: **Read + operational** (start/stop CLI commands from UI).
  - Access control: **Local-only** (bind `127.0.0.1`, no auth for MVP).
  - CSS: **Tailwind**.
  - Jobs concurrency: **single job at a time** (simple mutex).
  - Operational model: **Hybrid — subprocess CLI**: read endpoints query SQLite/JSON directly; operational endpoints spawn/kill the `mev-scout` binary as background jobs, capture stdout/stderr into logs.
- Architecture reference: `docs/ARCHITECTURE.md`; explorer data model: `core/src/explorer/store.rs` (table schemas + query methods).

## Data sources (read side)

- **Explorer store**: `core/src/explorer/store.rs` tables (`blocks`, `txs`, `transfers`, `swaps`, `mev_ops`, `labels`, `prices`, `sync_state`, `blocks_classified`, `opportunities`, `rejected_candidates`) — open read-only (WAL allows concurrent readers).
- **Scanner results**: `results/*.json` (`ResultsFile`), export dir from config (`Config::output.export_path`).
- **Scanner cache**: `cache/{chain}-mev-scout.sqlite` — run manifests (`RunManifest`), discovered pools.
- API returns serde types matching `MevOpRow`, `StatsRow`, `FeedRow`, `OverviewRow`, `OpportunityRow`, `RejectedRow` (already `Serialize`).

### Operational (jobs over subprocess)

| Method | Path | Body / Params | Response | Notes |
|--------|------|---------------|----------|-------|
| `POST` | `/api/jobs` | `{ command, args }` | `{ job_id }` | 409 if job already running; `command` must be in allowlist (see Safety) |
| `GET` | `/api/jobs` | — | `Vec<JobInfo>` | list all (running + finished) |
| `GET` | `/api/jobs/:id` | — | `JobInfo` | status, exit_code, run_id, created_at |
| `GET` | `/api/jobs/:id/log?tail=` | query param `tail` (default 100) | `Vec<String>` | log lines |
| `POST` | `/api/jobs/:id/stop` | — | `JobInfo` | kill process tree |

**Job = `tokio::process::Command`** running the `mev-scout` binary with resolved argv. stdout/stderr piped to `{data_dir}/logs/{job_id}.log` (where `data_dir` is alongside the binary or configurable, NOT inside the source tree). One running job at a time enforced by `Arc<Mutex<JobManager>>`.

**Safety**:
- No shell invocation (argv array only, `Command::new(path).args(vec![...])`)
- Config path validated (must exist, must be readable)
- Local bind only (`127.0.0.1`)
- **Command allowlist**: only these commands may be spawned: `run`, `live`, `fetch`, `discover`, `validate-pools`, `tokens`, `scan`, `replay`, `report`, `explorer index`, `explorer live-feed`, `explorer stats`, `explorer top`, `explorer show`, `explorer explain`, `explorer validate`, `explorer export`. Reject any other `command` with 400.
- Process tree kill on Windows: `taskkill /T /F /PID {child_pid}` (see Risks)

**Windows process tree kill**:
```rust
#[cfg(target_os = "windows")]
async fn kill_process_tree(pid: u32) -> anyhow::Result<()> {
    tokio::process::Command::new("taskkill")
        .args(["/T", "/F", "/PID", &pid.to_string()])
        .output()
        .await?;
    Ok(())
}

#[cfg(not(target_os = "windows"))]
async fn kill_process_tree(pid: u32) -> anyhow::Result<()> {
    // SIGTERM first, then SIGKILL after timeout
    nix::sys::signal::kill(unistd::Pid::from_raw(pid as i32), nix::sys::signal::Signal::SIGTERM)?;
    Ok(())
}
```

**Job → Run link**: After a job finishes with exit code 0, `JobInfo` includes `run_id: Option<String>` parsed from stdout (the CLI prints `Run ID: run_{epoch}` or `Run ID: live_{epoch}`). The frontend can then fetch `/api/results/{run_id}`. Regex: `Run ID: (run_\d+|live_\d+)`.

## Risks / notes

- **SQLite concurrent access**: API opens read-only connections (WAL) while CLI writes — safe; avoid API writes to avoid lock contention.
- **`ResultsFile` JSON parsing**: API reads `results/*.json` directly (same serde types as `MevOpportunity`). No duplication issue since the same types from `core` are used.
- **Windows process tree kill**: `Child::kill()` only kills the direct child, not grandchildren (e.g., if `mev-scout` spawns revm or async workers). Must use `taskkill /T /F /PID` on Windows. On Unix, `SIGTERM` to process group is sufficient (requires `nix` crate).
- **Pool name enrichment**: CLI uses `pool_manager.get()` to resolve addresses to human-readable names (DEX + tokens). API returns `PoolInfo` from cache which includes `dex_name`, `token0_symbol`, `token1_symbol` fields.
- **Live config files**: currently contain real API keys tracked in git — rotate before any public exposure. Use `${ENV_VAR}` pattern from `mev-scout.example.toml`. Add `mev-scout.toml`, `mev-scout.base.toml`, `mev-scout-arbitrum.toml` to `.gitignore`.
- **RPC key exposure**: `Config::rpc_urls` is NOT `#[serde(skip)]` — never serialize the full `Config` over the API. Create a sanitized `SanitizedConfig` DTO that omits `rpc_urls` and `rpc_rps`.
- **Pagination**: MVP slices `Vec<T>` in API layer (calls full store query, then takes `offset..offset+limit`). All `limit` params capped: feed=200, ops=500, pools=200, top=100. Sufficient for local-only use with reasonable data volumes. If data grows, add paginated SQL queries to store later. Future enhancement: cursor-based pagination (using `id` or `block_number`) for better live-tailing UX.
- **Missing DB graceful handling**: If explorer or cache DB doesn't exist yet (never indexed), read endpoints should return empty arrays/nulls with 200, not 500. Health endpoint reports `db_status: "missing"`.
- **Validation endpoint**: `GET /api/explorer/validate` removed from MVP — `ValidationReport` requires `compute_validation()` which is expensive and re-runs the comparison. Better served by caching the JSON output from CLI `explorer validate --json` and serving the cached file, or adding a job endpoint that runs it on demand.
- **CORS policy**: For dev (Vite `:5173` → API `:7600`), configure `Access-Control-Allow-Origin: http://localhost:5173`. For production (same-origin static serving), CORS not needed. Use `tower-http::cors::CorsLayer` with environment-aware origin.
- **Rate limiting**: Optional for MVP — consider `tower::limit::RateLimitLayer` (e.g., 10 req/s) to prevent misbehaving frontend tabs from hammering SQLite. Low priority.
- **Static asset caching**: For production, serve Vite hashed assets (`assets/*.js`, `assets/*.css`) with `Cache-Control: public, max-age=31536000, immutable`. Serve `index.html` with `Cache-Control: no-cache`. Use `tower-http::services::ServeDir` with `ServeFile::new().precompressed_br()`.
- **Log file location**: Job logs stored at `{data_dir}/logs/{job_id}.log` where `data_dir` defaults to a directory next to the binary (e.g., `./api_data/`). NOT inside the source tree. Add `api_data/` to `.gitignore`.
- **Database migration**: As the explorer schema evolves, API and CLI may run different versions. Consider adding a `schema_version` row to `sync_state` and checking it on API startup. Not needed for MVP since schema is stable.

## Out of scope (explicit)

- Auth/multi-user, HTTPS, remote deployment hardening.
- SSE/WebSocket streaming for feed (MVP uses polling at 10–30s intervals). Future: `GET /api/explorer/feed/stream` via `axum::response::sse`.
- SSE/WebSocket for job log streaming (MVP uses polling at 2s intervals). Future: `GET /api/jobs/:id/stream` for real-time log tail.
- Embedded in-process execution of core library functions (subprocess chosen).
- Embedded in-process explorer validation (CLI subprocess or cached JSON).
- Cursor-based pagination (future enhancement over offset pagination).
- Rate limiting / request throttling (future hardening).
