# Plan: mev-scout Web UI + API (same repo)

## Context

- Goal: a web UI covering the **critical CLI commands** (`run`, `live`), **auxiliary commands** (`discover`, `tokens`, `scan`, `report`), and `explorer index` (explorer store population), plus an API layer (user confirmed API is needed).
- **Results storage is SQLite-only** (codebase evolved past JSON exports): `run`/`live` write execution history to the cache store's `run_manifests` table and detections to the explorer store's `opportunities` table. There is **no `results/*.json` folder anymore** — all read endpoints query SQLite.
- Decisions made with user:
  - UI lives in **this repo** (workspace member, shared types with core).
  - Frontend stack: **React + Vite + TypeScript** (static build served by the API).
  - API scope: **Read + operational** (start/stop CLI commands from UI) + **config editing** (non-secret fields).
  - Access control: **Local-only** (bind `127.0.0.1`, no auth for MVP).
  - CSS: **Tailwind**.
  - Jobs concurrency: **single job at a time** (simple mutex).
  - Operational model: **Hybrid — subprocess CLI**: read endpoints query SQLite directly; operational endpoints spawn/kill the `mev-scout` binary as background jobs, capture stdout/stderr into logs.
  - **Chains: 7 supported** (polygon, avalanche, bsc, arbitrum, base, ethereum, optimism — `ChainName` enum). UI uses an **active-chain switch**: changing chain writes `chain = "…"` to the config file and the API re-resolves DB paths/connections. One chain active at a time.
  - **Config editing**: UI may edit **non-secret fields only** (chain, gas, backtest, output format, explorer). RPC secrets stay on disk and are never displayed or written through the API (secret-safe round-trip, see Config editing section).
  - **Live PnL is simulated**: mev-scout detects/simulates but never signs or sends transactions (no executor module). The "session report" sums expected profits minus gas per token — clearly labeled simulated. Real wallet execution = explicit out of scope, separate future plan.
  - **Backtest progress visualization via structured CLI events**: new `--progress json` flag emits NDJSON stage events the API parses for the UI (not indicatif bar parsing).
  - **Explorer cross-checks are automatic**: after a run completes, the UI shows a validation panel (T1/T2/T3 match per opportunity) computed in-process; if the explorer hasn't indexed the range, a one-click "Index this range" button queues an `explorer index` job then revalidates.
- Architecture reference: `docs/ARCHITECTURE.md`; explorer data model: `core/src/explorer/store.rs` (table schemas + query methods).

## Data sources (read side)

- **Explorer store** (`cache/explorer-{chain}.sqlite`): `core/src/explorer/store.rs` tables (`blocks`, `txs`, `transfers`, `swaps`, `mev_ops`, `labels`, `prices`, `sync_state`, `blocks_classified`, `opportunities`, `rejected_candidates`) — **single read-only `rusqlite::Connection` opened at startup in `AppState`**, WAL mode allows concurrent readers. Wrapped in `Mutex<Connection>` for thread safety.
- **Scanner cache** (`cache/{chain}-mev-scout.sqlite`): run manifests (`run_manifests` table — execution history; `list_manifests()` is new core work), discovered pools (`pool_info` table with `tvl_usd`, `volume_usd_24h`, `volume_usd_30d`, `dex_name`, `token0/1_symbol` columns). Second read-only connection, same pattern.
- **Scanner opportunities**: explorer store `opportunities` table — written by `run`/`live` via `persist_opportunities_to_explorer` (cli/src/display.rs). **This is the results layer** — read back via `opportunities_by_run(run_id)` (reconstructs `MevOpportunity` list) and `opportunities_in_range()`. No JSON files involved anywhere.
- **Prices for PnL USD conversion**: explorer `prices` table (best-effort; per-token USD values may be missing → PnL reports omit USD rather than fail).
- API returns serde types matching `MevOpRow`, `StatsRow`, `FeedRow`, `OverviewRow`, `OpportunityRow`, `RejectedRow`, `MevOpportunity`, `RunManifest` (all already `Serialize`).

**Chain switch**: both DB paths are derived from the active chain (`effective_db_path`, `effective_explorer_db_path`). `PUT /api/config {chain}` updates the config file and swaps both connections. Read endpoints always serve the active chain; historical data for other chains remains on disk, viewable by switching back.

## Config editing (PUT /api/config)

Edit flow (secret-safe):
1. API keeps the **raw `toml::Value` parse** of the config file (never the env-expanded in-memory `Config` — `Config::load` expands `${ENV_VAR}` secrets into memory at load time, so serializing that back to disk would bake real API keys into the file).
2. `PUT /api/config` accepts only non-secret fields: `chain`, `gas.*` (gas_model, gas_limit, priority_fee_gwei), `backtest.*` (strategies, flash_loan_provider, min_profit_wei, max_pairs_per_token, proximity_window, capture_pending, max_candidates_per_tx), `output.output`, `output.db_path` (SQLite dir — editing it re-resolves both DB paths like a chain change; the JSON `export_path` no longer exists), `explorer.*` (confirmations, poll_interval_ms, checkpoint_every, db_path).
3. Merge into the raw `toml::Value`, validate with core `validation::validate_and_resolve` (dry-run; 400 on invalid), back up the current file to `{config}.bak.toml`, then write.
4. RPC secrets (`rpc_url`, `rpc_urls`, `rpc_rps`): **preserved verbatim on disk, never returned in full, never editable**. `GET /api/config` shows masked summaries (provider count + hostname only).
5. If `chain` changed: re-resolve `effective_db_path`/`effective_explorer_db_path`, swap both `AppState` connections (RwLock write), refresh UI.

Jobs spawned after a chain switch pick up the new config file automatically (subprocess reads the same file). **Chain switching and config edits are rejected (409) while a job is running.**

**Security**: `Config` has `rpc_urls` containing API keys which are NOT `#[serde(skip)]`. Any endpoint returning config must strip/redact `rpc_urls` before serializing. Only return sanitized fields: `chain`, `strategies`, `gas_model`, `output`, chain-level metadata. **Add a test that serializes the full `Config` and asserts `rpc_urls` is absent from the output.**

### Operational (jobs over subprocess)

| Method | Path | Body / Params | Response | Notes |
|--------|------|---------------|----------|-------|
| `POST` | `/api/jobs` | `{ command, args, timeout_secs? }` | `{ job_id }` | 409 if job already running; `command` must be in allowlist (see Safety) |
| `GET` | `/api/jobs` | — | `Vec<JobInfo>` | list all (running + finished) |
| `GET` | `/api/jobs/:id` | — | `JobInfo` | status, exit_code, run_id, created_at |
| `GET` | `/api/jobs/:id/log?tail=` | query param `tail` (default 100) | `Vec<String>` | log lines |
| `GET` | `/api/jobs/:id/progress` | — | `{ stage, done?, total?, run_id?, pct? }` | **new** — parsed from the latest NDJSON `--progress json` event in the log; `stage: "resolve"\|"fetch"\|"pool_init"\|"detect"\|"complete"`; `null` progress for commands without the flag |
| `POST` | `/api/jobs/:id/stop` | — | `JobInfo` | kill process tree |

**Job = `tokio::process::Command`** running the `mev-scout` binary with resolved argv. stdout/stderr piped to `{data_dir}/logs/{job_id}.log` via two `tokio::io::copy` tasks reading from `child.stdout` and `child.stderr` respectively, appending to the same log file. One running job at a time enforced by `Arc<Mutex<JobManager>>`. Optional `timeout_secs` field in request body; if set, job is killed after timeout.

**Safety**:
- No shell invocation (argv array only, `Command::new(path).args(vec![...])`)
- Binary path resolved at startup: `std::env::current_exe()` parent → `{parent}/mev-scout` (or `--binary` flag override). Must exist and be executable.
- Config path validated (must exist, must be readable)
- Local bind only (`127.0.0.1`)
- **Command allowlist** (scoped to critical + auxiliary commands, user decision): only these commands may be spawned: `run`, `live`, `discover`, `tokens`, `scan`, `report`, `explorer index` (kept because it populates the explorer store the UI reads from). Reject any other `command` with 400. Explicitly excluded: `fetch`, `replay`, `config`, `validate-pools`, and read-side `explorer` subcommands (`live-feed`, `stats`, `top`, `show`, `explain`, `validate`, `export`) — these are covered by API read endpoints instead of subprocess jobs.
- Process tree kill on Windows: `taskkill /T /F /PID {child_pid}` (see Risks)

**Windows process tree kill**:
```rust
#[cfg(target_os = "windows")]
async fn kill_process_tree(pid: u32) -> anyhow::Result<()> {
    tokio::process::Command::new("taskkill")
        .args(["/T", "/F", "/PID", &pid.to_string()])
        .output()
        .await?;
    Ok(())
}

#[cfg(not(target_os = "windows"))]
async fn kill_process_tree(pid: u32) -> anyhow::Result<()> {
    // SIGTERM first, then SIGKILL after timeout
    nix::sys::signal::kill(unistd::Pid::from_raw(pid as i32), nix::sys::signal::Signal::SIGTERM)?;
    Ok(())
}
```

**Job → Run link**: The `run_id` is parsed from stdout **as soon as the `Run ID:` line appears** (not only at exit) so the Live Monitor can start streaming opportunities for a still-running `live` job. `JobInfo` includes `run_id: Option<String>` (also retained on the finished job). The frontend can then fetch `/api/results/{run_id}` and `/api/opportunities?run_id={run_id}`. Regex: `Run ID: (run_\d+|live_\d+)`. Note: `live` currently prints **no** `Run ID:` line (only `run`/`fetch` do) — phase 3.5 must add `println!("Run ID: {}", run_id)` to `live` (one-shot + loop paths), otherwise `JobInfo.run_id` stays null for live jobs and the `/live` streaming/final-report auto-fetch breaks. History survives API restarts via two persisted stores (the in-memory job list does not — failed/killed jobs vanish from `/api/jobs` after restart): all of `run`/`fetch`/`live` write a `RunManifest` row to the cache `run_manifests` table (queryable via `/api/runs`), and `run`/`live` write one `opportunities` row per detection (queryable via `/api/opportunities?run_id=…`). `/api/opportunities/runs` still powers the run_id dropdowns and provides a run-agnostic listing.

## CLI changes (required for UI scenarios)

Two small additions to `cli/src/cli.rs` + `core`:

1. **`--progress json` flag** (`run`, `live`): when set, the command emits one NDJSON event per line to **stdout** alongside normal output, replacing the indicatif bar (which contains control chars unusable by the log-collector):
   ```json
   {"stage":"resolve"}
   {"stage":"fetch","done":37,"total":500}
   {"stage":"pool_init"}
   {"stage":"detect","done":120,"total":500}
   {"stage":"complete","run_id":"run_1730000000","ops":14,"elapsed_ms":83210}
   ```
   Implementation: generalize the existing `Fetcher` tick closure (`Some(&tick)` at cli/src/commands/run.rs:88) into a progress-event callback threaded through fetch + detect stages. The API's LogCollector tail-parses these lines for `GET /api/jobs/:id/progress`.
2. **`--max-blocks N` flag** (`live` only, requires `--loop`): stop after N processed blocks (in addition to the existing `--duration`). Powers "number of runs / block count" live-launcher parameters.
3. **`println!("Run ID: {}", run_id)` for `live`** (both one-shot and loop paths, at `cli/src/commands/live.rs`): currently missing — only `run`/`fetch` print it. Without this, `JobInfo.run_id` stays null for live jobs, breaking the `/live` page's opportunity-stream link and the post-completion report auto-fetch. **Live Monitor page** (`/live`) is the purpose-built UX for `live --loop` (user decision) rather than a generic jobs preset. It reuses the jobs API under the hood (`POST /api/jobs` with `command: "live"`, `args: ["--loop", "--progress", "json", ...]`) and links the parsed `live_{epoch}` run ID to `/api/opportunities` for the stream. The single-job mutex still applies — if a job is already running (from `/jobs`, `/live`, or `/explorer` live mode), the launcher shows it and offers Stop.

**Backtest Runner page** (`/run`) similarly wraps `POST /api/jobs` with `command: "run"`, always adding `--progress json`. When the job completes, the UI auto-fetches `/api/results/{run_id}`, `/api/results/{run_id}/validation`, and `/api/results/{run_id}/pnl` for the final report.

### API client error handling (`api.ts`)

- All fetch calls wrapped in a helper that checks `response.ok` before parsing.
- On 4xx/5xx: throw typed `ApiError` with status + message.
- Components use `ErrorBoundary` for render errors; API call errors shown via `Toast`.
- No automatic retries (local-only, fast failures preferred).

## Risks / notes

- **SQLite concurrent access**: API opens read-only connections (WAL) while CLI writes — safe; avoid API writes to avoid lock contention.
- **`ResultsFile` reconstruction**: run detail is rebuilt API-side from `RunManifest` + `opportunities_by_run()` (same reconstruction `cli report` uses). Fields not persisted in the `opportunities` table (raw/slippage profit variants, JIT tick bounds, sandwich victim/backrun indices) come back as defaults — documented in store.rs; the UI renders persisted fields only.
- **Windows process tree kill**: `Child::kill()` only kills the direct child, not grandchildren (e.g., if `mev-scout` spawns revm or async workers). Must use `taskkill /T /F /PID` on Windows. On Unix, `SIGTERM` to process group is sufficient (requires `nix` crate).
- **Graceful shutdown**: On `ctrl_c`, the API must kill all running child jobs before exiting. `JobManager` tracks all `Child` handles; shutdown handler iterates and calls `kill_process_tree` on each. Use `tokio::select!` on `ctrl_c` + main loop to trigger cleanup.
- **Pool name enrichment**: CLI uses `pool_manager.get()` to resolve addresses to human-readable names (DEX + tokens). API returns `PoolInfo` from cache which includes `dex_name`, `token0_symbol`, `token1_symbol` fields.
- **Live config files**: currently contain real API keys tracked in git — rotate before any public exposure. Use `${ENV_VAR}` pattern from `mev-scout.example.toml`. Add `mev-scout.toml`, `mev-scout.base.toml`, `mev-scout-arbitrum.toml` to `.gitignore`.
- **RPC key exposure**: `Config::rpc_urls` is NOT `#[serde(skip)]` — never serialize the full `Config` over the API. Create a sanitized `SanitizedConfig` DTO that omits `rpc_urls` and `rpc_rps`.
- **Pagination**: MVP slices `Vec<T>` in API layer (calls full store query, then takes `offset..offset+limit`). All `limit` params capped: feed=200, ops=500, pools=1000, top=100, results=100, runs=100, opportunities=500. Sufficient for local-only use with reasonable data volumes. If data grows, add paginated SQL queries to store later. Future enhancement: cursor-based pagination (using `id` or `block_number`) for better live-tailing UX.
- **Missing DB graceful handling**: If explorer or cache DB doesn't exist yet (never indexed), read endpoints should return empty arrays/nulls with 200, not 500. Health endpoint reports `db_status: "missing"` (file not found) or `"corrupt"` (file exists but connection fails).
- **Validation endpoint**: `GET /api/results/:run_id/validation` computes in-process via `compute_validation()` run-filtered — cheap for typical backtest ranges (tens–hundreds of blocks). For very large windows the UI shows a "this may take a moment" state; the expensive full/unfiltered `explorer validate` remains CLI-only.
- **Config write risks**: (a) env-secret preservation — always round-trip the raw TOML value, never the expanded `Config` (see Config editing); (b) backup file `{config}.bak.toml` overwritten on each edit — single-level undo; (c) concurrent CLI runs started outside the API won't see UI edits until they exit — acceptable for local single-user; (d) chain switch while a job runs is rejected (409) to avoid a job writing to a different chain's DB than the UI is displaying.
- **PnL semantics (simulated)**: expected_profit/gas come from simulation (`MevOpportunity`), not realized execution. Gas is denominated in **native wei** while `expected_profit` is in `token_out` units — so per-token `net` (gross − gas) is only meaningful when the profit token ≈ native/stable and is otherwise a display heuristic; the API must subtract gas only in that case and compute totals in USD via `prices`. USD conversion depends on the explorer `prices` table having values for the profit tokens in the run's blocks — when missing, USD columns are omitted (never fabricated). The report is always labeled simulated; mev-scout has no transaction-execution module.
- **Pool TVL availability**: `tvl_usd`/`volume_*` columns are populated only by remote enrichment (`discover --enrich`); onchain-only discovery leaves them null. The Pools page detects all-null and shows the "Enrich pools" action instead of broken sort UI.
- **Live mode feed latency**: explorer `--live` indexing applies a confirmation lag (default 6 blocks) before a block becomes visible in the feed — the Live mode indicator must communicate "indexed head", not chain head (from `/api/sync`).
- **Progress-event robustness**: NDJSON events and human output share stdout; the parser must skip non-JSON lines (log lines, tables). Prefix events with a distinctive marker or emit to a dedicated line format (e.g. leading `@progress ` JSON) if parse collisions occur.
- **CORS policy**: For dev (Vite `:5173` → API `:7600`), configure `Access-Control-Allow-Origin: http://localhost:5173`. For production (same-origin static serving), CORS not needed. Detect environment via `ENV=development` env var or `cfg(debug_assertions)`. Use `tower-http::cors::CorsLayer`.
- **Rate limiting**: Optional for MVP — consider `tower::limit::RateLimitLayer` (e.g., 10 req/s) to prevent misbehaving frontend tabs from hammering SQLite. Low priority.
- **Static asset caching**: For production, serve Vite hashed assets (`assets/*.js`, `assets/*.css`) with `Cache-Control: public, max-age=31536000, immutable`. Serve `index.html` with `Cache-Control: no-cache`. Use `tower-http::services::ServeDir` with `ServeFile::new().precompressed_br()`.
- **Content-Type headers**: Axum sets `application/json` automatically for `Json<T>` responses. `tower-http`'s `ServeDir` infers MIME types from file extensions (`.js`, `.css`, `.svg`, `.wasm`); verify `.wasm`/`.br` variants are served with correct `Content-Type` if precompressed assets are used.
- **Log file location**: Job logs stored at `{data_dir}/logs/{job_id}.log` where `data_dir` defaults to a directory next to the binary (e.g., `./api_data/`). NOT inside the source tree. Add `api_data/` to `.gitignore`. Also add `web/dist/` (frontend build output).
- **Database migration**: As the explorer schema evolves, API and CLI may run different versions. Consider adding a `schema_version` row to `sync_state` and checking it on API startup. Not needed for MVP since schema is stable.

## Out of scope (explicit)

- **Real wallet execution** (tx signing, `eth_sendRawTransaction`, fund management, on-chain settlement). The PnL report is simulated accounting over detected opportunities only. An executor module would be a separate core feature + plan.
- Adding more chains beyond the 7 supported (would require `ChainName` enum, `chains.toml`, RPC endpoints, labels — core work independent of the UI).
- Multi-chain simultaneous browsing (active-chain switch chosen; per-chain DBs remain on disk and are viewable by switching).
- Auth/multi-user, HTTPS, remote deployment hardening.
- SSE/WebSocket streaming for feed (MVP uses polling at 5–30s intervals). Future: `GET /api/explorer/feed/stream` via `axum::response::sse`.
- SSE/WebSocket for job log streaming (MVP uses polling at 2s intervals). Future: `GET /api/jobs/:id/stream` for real-time log tail.
- Embedded in-process execution of core library functions (subprocess chosen).
- Cursor-based pagination (future enhancement over offset pagination).
- Rate limiting / request throttling (future hardening).
